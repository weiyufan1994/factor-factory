# Factor Forge Ultimate Epistemic Advisory Operating Delta v1

This reference activates one local, candidate-only research advisory route for
the Ultimate skill. It changes retrieval timing and agent ergonomics; it does
not change formal Factor Forge authority, Step artifact schemas, OOS controls,
Council decisions, qualification, promotion, or canonical memory.

Read this file completely for either of these tasks:

- a new report, user hypothesis, formula idea, or other source-led intake;
- advisory analysis of a Step4/Step5 underperformance or failure.

The current operating contract remains normative. This delta has precedence
only for the retrieval timing and advisory consumption rules named below.

## User-facing entry

The user invokes `factor-forge-ultimate`. Do not ask the user to configure RAG,
select knowledge-index files, mint a session secret, run a sidecar command, or
copy a shadow request. Those are internal Ultimate-agent duties.

The deterministic bridge configures only canonical repository knowledge paths,
the fixed A0 lane set, `top_k_per_lane=3`, and one fresh per-attempt secret. It
does not author economic semantics. The current research agent must read the
source and author the source-only overlay itself.

## New-source sequence

For a new source, use this exact order:

1. Inspect repository/worktree state and create or select the one native factor
   workspace required by the current operating contract.
2. Read the report or the user's hypothesis in source-only context. Do not open
   factor knowledge, historical cases, current-factor results, code or data
   availability while performing this first understanding pass.
3. Distinguish source-native claims, agent paraphrases, agent inferences, new
   assumptions and unresolved items. Novel source language is allowed; do not
   force a taxonomy or mathematical family onto it.
4. Freeze a candidate source-faithful formalization or a lawful abstention. A
   formalized overlay must name the payer/constraint, estimand, information set,
   horizon, mathematical object, observation map, expected failure signature,
   falsifiers, material rivals, provenance and pre-A0 predictions.
5. Only after that freeze, run the Source-First advisory bridge and dedicated
   package validator. Consume only the advisory JSON bytes emitted by that
   successful validator as priors, analogies, counterexamples and tool
   candidates; do not reopen `01_chief_advisory.json` by path.
6. Author the formal Step1 conjecture and subsequent mathematical model from
   the source-first record plus explicitly attributed advisory reasoning. Never
   rewrite the frozen source understanding or present a retrieved idea as a
   source-native claim.
7. Continue formal execution through the exact Ultimate wrapper and gates in
   the current operating contract.

This sequence ensures that Step1 first understands the source. RAG may broaden
the later model search, but it cannot select the current estimand, payer,
mechanism, sign or mathematical object by historical performance.

## Agent-authored overlay

Write one closed JSON object under:

```text
<factor-workspace>/candidate_epistemic_shadow_inputs/source-first-overlay.json
```

Use the semantic shapes in
`examples/factorforge_epistemic_kernel_wavelet_demo_input.json` for these seven
fields only:

- `source_text`
- `source_lineage`
- `author_claims`
- `analyst_notes`
- `selected_semantic_body`
- `formalization_provenance`
- `pre_a0_predictions`

Add:

```json
{
  "schema_id": "factorforge_epistemic_agent_source_first_overlay_v1",
  "schema_version": "1.0.0",
  "report_id": "<current-report-id>",
  "agent_source_only_attestation": {
    "attestation_mode": "AGENT_CLAIMED_SOURCE_ONLY_PRE_RETRIEVAL__NOT_INDEPENDENTLY_VERIFIED",
    "source_understanding_completed_before_retrieval": true,
    "knowledge_or_case_retrieval_consulted": false,
    "current_factor_metrics_or_oos_consulted": false,
    "semantic_fields_authored_by_current_research_agent": true,
    "independent_pre_retrieval_attestation_present": false
  }
}
```

The attestation is intentionally caller-claimed, not proof of a blind state.
Never set clean/verified/ex-ante fields by default. If the original source,
legal-availability time, source locator, selection lineage, outcome exposure or
semantic provenance cannot be established, the new-source formal intake must
BLOCK for clarification or end in lawful abstention. This is a semantic
prerequisite failure, not a nonblocking RAG outage. Do not reconstruct the
source from `alpha_idea_master`.

## Automatic bridge command

Run this before using historical knowledge to author the formal conjecture:

```bash
python3 scripts/run_factorforge_epistemic_source_first_advisory.py \
  --factor-workspace <factor-workspace> \
  --report-id <report-id> \
  --source-first-overlay \
    <factor-workspace>/candidate_epistemic_shadow_inputs/source-first-overlay.json
```

No RAG path, lane, secret, Host credential or OOS argument is accepted. The
bridge compiles the Source-First seed before it resolves canonical knowledge
indexes. It publishes an exact-three candidate package under
`candidate_epistemic_shadow/` and removes the session secret from all package
files.

## Candidate package validation and retry

The consumption order is mandatory:

1. run the Source-First bridge;
2. run the dedicated candidate-package validator against the produced exact-three
   package;
3. consume the advisory JSON bytes emitted from the validator's already-
   verified in-memory object; never reopen `01_chief_advisory.json` by path.

The validator receives the expected Factor Forge root from the active Ultimate
operating context and proves the workspace is under that externally bound root.
A workspace manifest is an input to that check; it cannot self-certify the
expected root or substitute a caller-selected root.

The bridge and validator use one stable attempt state for one source-first
attempt. A retry must reload and validate or resume that state; it must not mint
another attempt or publish another candidate package. Missing, conflicting or
drifted attempt state is `BLOCKED` for advisory consumption.

Attempt identity binds the compiled Source-First record and the exact canonical
knowledge-file snapshot. Unchanged inputs retry idempotently; a legitimate
knowledge snapshot change creates a new content-addressed attempt instead of
silently invalidating or overwriting the old package.

Only the validator-emitted bytes from a passed package may be read by the current research agent. It
is not a direct input to formal Step1–6 scripts, proof, Council, qualification
or promotion. If the agent uses an advisory idea later, record it as an advisory
prior, counterexample, tool candidate, agent inference or new assumption with
its provenance; never as current-factor evidence.

## Exploit and Explore

The advisory queue has two independent lanes:

- `exploit`: reuse or adapt a structurally relevant precedent;
- `explore`: investigate a mechanism-distinct mathematical or economic route.

Each lane contains `0..N` candidates. Empty Exploit, empty Explore, or Neither
is a valid abstention. Never fabricate a dummy branch.

This does not replace the current formal Step6 multi-branch validator. Candidate
lane items must not be copied directly into formal synthesis, child
materialization or Step3B handoff. A formal revision still requires the current
Step6/Council contract and explicit human approval.

## Post-Step5 failure advisory

The existing failure sidecar remains available only when its exact candidate
diagnosis inputs are already valid. Its output may supply:

- material rival candidates;
- distinguishing-test plans;
- layer-local questions;
- future-question anchors;
- advisory Exploit/Explore possibilities.

It may not execute a diagnostic test, identify a cause, clear a lower layer,
qualify a factor, revise the current trial, feed Council as evidence, or mutate
Step3B. Any explanation first generated after results are visible belongs to
the future-question namespace and cannot be written back into the current
diagnosis, qualification or revision.

Do not synthesize the current failure fixture or assertion DAG from metrics.
When a valid diagnosis seed is absent, record
`ADVISORY_NOT_RUN__DIAGNOSIS_SEED_UNAVAILABLE` and continue the formal pipeline.
A real formal-Step5 diagnosis-seed adapter requires a separate reviewed
operating-contract delta.

## Failure and negative authority

After a valid source-only freeze exists, operational advisory failures are
nonblocking: unavailable indexes, zero retrieval hits, a bridge runtime failure,
a blocked post-Step5 sidecar or an unavailable diagnosis seed must be reported,
but cannot change the formal wrapper return code, command closure, proof
eligibility or factor verdict.

An invalid or missing source overlay is different. For a new-source route it
means the mandatory source-semantic prerequisite is absent, so formal intake
must BLOCK for clarification or record lawful abstention before any Step2–6
execution. It cannot be bypassed as a cold-start retrieval failure. Because the
formal run must not start in that state, this blocker never rewrites an existing
formal proof or verdict.

Every bridge/shadow artifact remains:

- `candidate_only=true`
- `signed=false`
- `authority_effect=NONE`

`canonical_memory_or_oos_accessed=false` means that neither canonical memory nor OOS
was accessed. It does not deny the bridge's separately declared read of public
repository knowledge indexes. The route has no Host, canonical-memory write,
OOS, production, network, deployment, qualification, promotion, training or
official writeback authority.
